\section{Introduzione}
\subsection{Scopo del documento} \label{sec:scopo_documento}
Il presente documento ha lo scopo di fornire una descrizione completa, formale e strutturata del prodotto software, delineandone in modo rigoroso le caratteristiche tecniche e architetturali.

La \term{Specifica Tecnica} rappresenta il riferimento principale per tutte le attività di progettazione, sviluppo, \term{Verifica} e manutenzione del sistema, assicurando coerenza rispetto ai requisiti definiti nel documento di \term{Analisi dei requisiti} e alle scelte progettuali adottate.

In particolare, il documento si propone di:

\begin{itemize}
    \item Definire l'\term{Architettura} complessiva del sistema, descrivendo le componenti software, le loro responsabilità e le modalità di interazione attraverso appositi diagrammi
    
    \item Specificare i moduli funzionali e le interfacce esposte, includendo i contratti di comunicazione e i formati dei dati scambiati
    
    \item Descrivere l'\term{Architettura} di \term{Deployment}, evidenziando la distribuzione delle componenti nei diversi ambienti di esecuzione e le relative dipendenze infrastrutturali
    
    \item Documentare le tecnologie, i linguaggi di programmazione, i \term{Framework} e gli strumenti adottati, motivando le scelte effettuate in relazione ai requisiti di progetto e al \term{Capitolato}
    
    \item Illustrare i principali design pattern e le soluzioni architetturali utilizzate, con particolare attenzione agli aspetti di scalabilità, manutenibilità e sicurezza
        
    \item Fornire indicazioni sui metodi di testing e di \term{Validazione}
    
    \item Supportare le attività di evoluzione e manutenzione del software, garantendo una base documentale chiara e coerente.
\end{itemize}

\section{Tecnologie} \label{sec:tecnologie}
Le tecnologie utilizzate sono state scelte trovando un punto d'incontro tra la necessità di garantire la sicurezza e la tutela dei dati personali degli utenti e il bisogno di realizzare un'\term{Architettura} solida, modulare e facilmente estendibile. Di seguito sono riportate tutte le tecnologie adottate 
\subsection{Framework} \label{subsec:framework}

\subsubsection{Flutter}
Flutter è un \term{Framework} open-source sviluppato da Google per la creazione di applicazioni multi-piattaforma a partire da un unico codice sorgente. Consente di sviluppare interfacce per dispositivi mobili, web e desktop utilizzando il linguaggio Dart. Flutter si basa su un sistema di widget componibili, che possono rappresentare qualsiasi elemento dell’interfaccia \term{Utente}. Flutter include un proprio motore grafico (come Impeller o storicamente Skia) che disegna direttamente i componenti a schermo, garantendo elevata coerenza visiva e prestazioni indipendenti dalla piattaforma sottostante. È il \term{Framework} alla base dell'App Che Protegge e Trasforma, il che consente di poter generare build per iOS e Android da un unico codice sorgente, a fronte di un maggiore utilizzo di risorse rispetto alle soluzioni native e di una minore possibilità di controllo diretto e personalizzazione delle funzionalità native della piattaforma.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 3.41.6
    \item \textbf{Documentazione}: \url{https://docs.flutter.dev/}
\end{itemize}

\subsection{Linguaggi di programmazione} \label{subsec:linguaggi}

\subsubsection{Dart}
Dart è un linguaggio di programmazione sviluppato da Google, progettato per la realizzazione di applicazioni client moderne. È un linguaggio tipizzato (con supporto sia statico che dinamico) e orientato agli oggetti. Viene utilizzato principalmente in combinazione con Flutter, dove il codice Dart viene compilato ahead-of-time in codice nativo per migliorare le prestazioni, oppure eseguito tramite compilazione just-in-time durante lo sviluppo. L'utilizzo di Flutter rende di fatto quasi obbligatoria l'adozione di Dart come linguaggio.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 3.11.4
    \item \textbf{Documentazione}: \url{https://dart.dev/docs}
\end{itemize}

\subsubsection{Python}
Python è un linguaggio di programmazione ad alto livello, interpretato e orientato agli oggetti, noto per la sua sintassi semplice e leggibile. Il codice Python viene eseguito da un interprete che traduce le istruzioni in bytecode, poi eseguito dalla macchina virtuale Python. Nel progetto è utilizzato lato \term{Backend} per la scrittura delle funzioni AWS Lambda e per i test tramite Pytest.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 3.14.3
    \item \textbf{Documentazione}: \url{https://docs.python.org/3/}
\end{itemize}

\subsection{Servizi AWS} \label{subsec:aws}

\subsubsection{Lambda}
AWS Lambda è un servizio \term{Serverless} che consente di eseguire codice senza gestire direttamente server o infrastruttura. Le funzioni vengono attivate in risposta a eventi e scalano automaticamente in base al carico. Nel progetto è utilizzato per implementare la logica \term{Backend}, eseguendo funzioni scritte in Python invocate tramite API Gateway.
\begin{itemize}
    \item \textbf{Versione utilizzata}: Runtime Python 3.14
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/lambda/}
\end{itemize}

\subsubsection{API Gateway}
AWS API Gateway è un servizio che permette di creare, pubblicare e gestire \term{API REST} e HTTP, fungendo da punto di ingresso per le richieste client. Gestisce autenticazione, routing e integrazione con altri servizi AWS. Nel progetto è utilizzato per esporre endpoint HTTP che invocano le funzioni Lambda.
\begin{itemize}
    \item \textbf{Versione utilizzata}: HTTP API (v2)
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/apigateway/}
\end{itemize}

\subsubsection{DynamoDB}
Amazon DynamoDB è un database NoSQL completamente gestito, progettato per offrire alte prestazioni e scalabilità automatica. I dati sono memorizzati in tabelle con chiavi primarie e accessibili con bassa latenza. Nel progetto è utilizzato per memorizzare dati strutturati come le note testuali del diario criptato e le chat con il chatbot.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/dynamodb/}
\end{itemize}

\subsubsection{S3}
Amazon S3 (Simple Storage Service) è un servizio di storage a oggetti che consente di archiviare e recuperare dati in modo scalabile e sicuro. I file sono organizzati in bucket e accessibili tramite API. Nel progetto è utilizzato per memorizzare contenuti multimediali come immagini e file audio.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/s3/}
\end{itemize}

\subsubsection{Cognito}
Amazon Cognito è un servizio di gestione delle identità che consente autenticazione, autorizzazione e gestione degli utenti. Supporta integrazione con provider esterni come Google. Nel progetto è utilizzato per gestire l’autenticazione degli utenti tramite account Google e per il controllo degli accessi.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/cognito/}
\end{itemize}

\subsubsection{Bedrock}
Amazon Bedrock è un servizio che consente di utilizzare modelli di intelligenza artificiale generativa tramite API, senza gestire direttamente l’infrastruttura sottostante. Permette l’accesso a diversi modelli foundation per task come generazione di testo. Nel progetto è utilizzato per implementare la funzionalità di chatbot.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/bedrock/}
\end{itemize}

\subsubsection{SES}
Amazon SES (Simple Email Service) è un servizio per l’invio e la ricezione di email in modo scalabile e affidabile. Supporta integrazione via API e SMTP. Nel progetto è utilizzato per inviare email ai contatti fidati degli utenti.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/ses/}
\end{itemize}

\subsubsection{CloudWatch}
Amazon CloudWatch è un servizio di monitoraggio e osservabilità che raccoglie metriche, log ed eventi dai servizi AWS. Consente analisi, visualizzazione e configurazione di allarmi. Nel progetto è utilizzato per la raccolta e l’analisi dei log generati dalle funzioni Lambda.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/cloudwatch/}
\end{itemize}

\subsubsection{EventBridge}
Amazon EventBridge è un servizio di event bus \term{Serverless} che consente di gestire e instradare eventi tra diversi servizi AWS. Esso permette di definire regole per reagire automaticamente a eventi generati da servizi AWS o da fonti esterne. Nel progetto è utilizzato per orchestrare i flussi di controllo di utilizzo dell'app da parte degli utenti, e l'invio delle email secondo le tempistiche stabilite dal Dead man's switch.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/eventbridge/}
\end{itemize}

\subsubsection{SAM}
AWS \term{Serverless} Application Model (SAM) è un \term{Framework} open-source che semplifica la definizione e il \term{Deployment} di applicazioni \term{Serverless} su AWS. Estende AWS CloudFormation introducendo una sintassi più compatta per risorse come Lambda, API Gateway e DynamoDB e include strumenti per build, testing locale e deploy delle applicazioni. Nel progetto è utilizzato per definire e distribuire l’infrastruttura \term{Serverless} in modo semplificato.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/serverless-application-model/}
\end{itemize}

\subsubsection{CloudFormation}
AWS CloudFormation è un servizio di \term{Infrastructure as Code} che consente di modellare e gestire risorse AWS tramite template dichiarativi in formato \term{YAML} o JSON. Nel progetto è utilizzato come base per il provisioning dell’infrastruttura, anche tramite template generati da SAM.
\begin{itemize}
    \item \textbf{Documentazione}: \url{https://docs.aws.amazon.com/cloudformation/}
    \item \textbf{Versioni}: CloudFormation non prevede versioni di servizio esplicite; eventuali aggiornamenti sono gestiti direttamente da AWS. I template possono però utilizzare versioni di specifiche risorse e trasformazioni (es. AWS::\term{Serverless}).
\end{itemize}

\subsection{Librerie} \label{subsec:librerie}

\subsubsection{http.dart}
http è una libreria per il linguaggio Dart che consente di effettuare richieste HTTP in modo semplice e asincrono. Fornisce metodi per eseguire operazioni come GET, POST, PUT e DELETE, gestendo automaticamente la serializzazione delle richieste e la ricezione delle risposte. È progettata per essere leggera e facilmente integrabile in applicazioni client.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 1.6.0
    \item \textbf{Documentazione}: \url{https://pub.dev/packages/http}
\end{itemize}

\subsubsection{image\_picker.dart}
\texttt{image\_picker} è una libreria Flutter che permette di accedere alla fotocamera e alla galleria del dispositivo per selezionare o acquisire immagini e video. Fornisce un’interfaccia unificata tra piattaforme diverse, gestendo le differenze tra iOS e Android.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 1.2.1
    \item \textbf{Documentazione}: \url{https://pub.dev/packages/image_picker}
\end{itemize}

\subsubsection{path\_provider.dart}
\texttt{path\_provider} è una libreria Flutter che consente di ottenere i percorsi delle directory del file system del dispositivo, come directory temporanee o documenti applicativi. Facilita l’accesso a percorsi corretti e compatibili tra piattaforme per la gestione dei file.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 2.1.5
    \item \textbf{Documentazione}: \url{https://pub.dev/packages/path_provider}
\end{itemize}

\subsubsection{provider}
\texttt{provider} è una libreria per Flutter che offre un meccanismo di gestione dello stato e di propagazione delle dipendenze lungo l'albero dei widget. Si basa sul sistema nativo di \texttt{InheritedWidget} di Flutter, semplificandone notevolmente l'utilizzo attraverso un'API dichiarativa. Consente di rendere disponibili oggetti (come i ViewModel) a interi sottoalberi dell'interfaccia, facilitando la comunicazione reattiva tra i layer dell'applicazione.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 6.1.5+1
    \item \textbf{Documentazione}: \url{https://pub.dev/packages/provider}
\end{itemize}

\subsubsection{url\_launcher}
\texttt{url\_launcher} è una libreria Flutter che consente di aprire URL nel browser predefinito del dispositivo, avviare applicazioni di posta elettronica, effettuare chiamate telefoniche o aprire altri tipi di risorse tramite i rispettivi handler nativi. Fornisce un'interfaccia unificata e compatibile tra le diverse piattaforme supportate da Flutter.
\begin{itemize}
    \item \textbf{Versione utilizzata}: 6.3.2
    \item \textbf{Documentazione}: \url{https://pub.dev/packages/url_launcher}
\end{itemize}

\subsubsection{flutter\_dotenv}
\texttt{flutter\_dotenv} è una libreria che permette di caricare variabili di configurazione da un file \texttt{.env} all'interno di un'applicazione Flutter. Consente di separare le configurazioni sensibili o dipendenti dall'ambiente (come chiavi API o endpoint) dal codice sorgente, rendendo più agevole la gestione di ambienti diversi senza modificare il codice dell'applicazione.

\section{Architettura}
\subsection{Architettura logica} \label{subsec:architettura_logica}

Il sistema software è progettato secondo i princìpi di un'\textbf{\term{Architettura a Strati}} (o \textit{Layered Architecture}), che impone una chiara separazione delle responsabilità tra i diversi livelli applicativi del sistema.
L'obiettivo cardine di questa scelta è massimizzare l'indipendenza formale della logica di business dalle interfacce grafiche \term{Utente} e dai meccanismi fisici di gestione del dato, favorendo così la facilità di test, la manutenzione nel tempo e il forte disaccoppiamento (\textit{\term{Separation of Concerns}}).

All'ingresso superiore dell'applicazione si posiziona l'ecosistema logico del dispositivo, mentre le fondamenta sono governate e calcolate dall'infrastruttura di servizio. L'interfaccia tra questi due mondi è ben definita tramite API e totalmente slegata dai linguaggi di programmazione o dai sistemi operativi utilizzati.

\subsubsection{Livello Client (Frontend Mobile)}
Il client mobile è sviluppato incapsulando il codice secondo i dettami moderni di una \textit{\term{Clean Architecture}} (fortemente affine al noto pattern architetturale \textit{Model-View-ViewModel} - MVVM). Il codice dell'applicazione è suddiviso in almeno tre strati logici indipendenti e gerarchici:

\begin{itemize}
    \item \textbf{Presentation Layer (View)}: Costituisce il livello più visibile e frontale dell'applicazione. Riceve gli input da parte dell'\term{Utente} e si occupa unicamente di aggregare e renderizzare il layout grafico a schermo tramite widget componenti, senza mai eseguire logica complessa.
    \item \textbf{\term{State Management} Layer (ViewModel)}: Funge da mediatore tra View e dominio, gestendo lo stato della view. Riceve input dalla view, muta lo stato dell'UI e notifica la view che si aggiornerà sulla base del nuovo stato incapsulato (es. passando da "In caricamento" a "Successo"). Inoltre, gestisce le validazioni elementari dei dati inseriti, comandando ai servizi sottostanti le operazioni formali da compiere.
    \item \textbf{\term{Data Layer}}: È lo strato più basso dell'ambiente Client, incaricato unicamente dell'acquisizione e gestione dei dati, ed è logicamente suddiviso in \textit{Service} e \textit{\term{Repository}}. I Service sono gli unici componenti ad interfacciarsi con l'esterno, conoscendo gli endpoint del \term{Backend} per eseguire le chiamate asincrone HTTP e gestendo l'accesso a dati memorizzati localmente o in remoto. I \term{Repository} fungono da intermediari: raccolgono i dati grezzi provenienti dai Service e li formattano in modelli di dominio strutturati (es. un oggetto \textit{Note}), fornendoli al ViewModel puliti e pronti all'uso.
\end{itemize}

\subsubsection{Livello di Servizio (Backend)}
L'\term{Architettura} logica adibita all'interazione tra i device mobili e l'ambiente computazionale in \term{Cloud} si fonda su un analogo approccio modulare disaccoppiato in tre sotto-livelli principali:

\begin{itemize}
    \item \textbf{Presentation e Routing Layer}: Costituisce il \textit{\term{Single Point of Entry}} dell'infrastruttura esposto al software. Ha la pura e unica responsabilità di tracciare e smistare le richieste esterne verso i rami corretti. Intercetta validazioni e autorizzazioni per poi rilasciare formalmente il \term{Payload} agli strati contigui.
    \item \textbf{Business Core / Logic Layer}: Costituisce il cuore elaborativo del sistema, dove risiede l'intera \textit{\term{Business Logic}}. Questo strato è implementato tramite unità funzionali indipendenti e distribuite (\textit{Funzioni Lambda}) ed è progettato per essere completamente agnostico rispetto ai dettagli di trasporto e comunicazione (come il protocollo HTTP). Il suo compito esclusivo è ricevere i dati già validati dal livello di \textit{Routing}, applicare le regole di dominio, coordinare l'elaborazione degli eventi asincroni e restituire le informazioni elaborate e strutturate.
    \item \textbf{\term{Data Access Layer}}: Un livello totalmente passivo e disaccoppiato che offre un'astrazione tramite moduli e \term{Driver}. Consente una persistenza dati logica e mascherata ai database sottostanti (quali storage documentali, array non relazionali o conservazione audio/video grezza), celando alla logica di business i layer fisici o i linguaggi di interrogazione diretti della persistenza \term{Cloud}.
\end{itemize}

\subsection{Design pattern utilizzati} \label{subsec:design_pattern}
\subsubsection{Model-view-viewmodel}
\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{diagrammi_classi/pattern_utilizzati/PatternMVVM.pdf}
    \caption{Rappresentazione del pattern MVVM nel modulo di Autenticazione}
    \label{fig:pattern_mvvm}
\end{figure}
\paragraph{Descrizione del pattern:}\mbox{}\\
Il pattern MVVM prevede la separazione tra la resa grafica, la \term{Presentation Logic} e la \term{Business Logic} in tre componenti principali:
\begin{itemize}
    \item \textbf{Model:} contiene il codice responsabile per la \term{Business Logic} dell'applicazione.
    \item \textbf{View:} contiene la parte responsabile esclusivamente per la resa grafica del software, e delega la gestione dell'interazione dell'\term{Utente} alla componente \textit{ViewModel}.
    \item \textbf{ViewModel:} contiene il codice responsabile per la gestione della \term{Presentation Logic} e per la coordinazione tra i componenti \textit{View} e \textit{Model}.
\end{itemize}
Nel contesto del \term{Framework} Flutter, l'implementazione di questo pattern viene riadattata per assecondare la natura dichiarativa dell'interfaccia. Nello specifico, il ViewModel è tipicamente implementato sfruttando una classe o un mixin proprietario chiamato \code{ChangeNotifier}, il quale consente di notificare esplicitamente la View dei cambiamenti di stato interno. La View, composta a sua volta da Widget, ascolta reattivamente tali notifiche potendo ricostruire e aggiornare solo le specifiche porzioni grafiche necessarie.
\paragraph{Ragioni per l'utilizzo:}\mbox{}\\
L'utilizzo del pattern espone notevoli vantaggi poiché permette una più semplice ed efficace gestione delle varie parti dell'applicazione limitando il forte accoppiamento (\textit{coupling}) tra l'interfaccia \term{Utente} visiva e la logica di business o di presentazione sottostante. Questo netto disaccoppiamento esalta la manutenibilità del codice dell'applicativo nel tempo e agevola considerevolmente lo sviluppo e l'esecuzione degli unit test, in quanto permette di testare i ViewModel e i Model isolandoli dal \term{Ciclo di vita} visivo tipico del sistema operativo e del \term{Framework}.
\paragraph{Riferimenti nel progetto:}\mbox{}\\
Il pattern MVVM è ampiamente utilizzato per strutturare l’interfaccia utente dell'applicazione e la logica ad essa associata, separando la resa grafica dalla gestione dello stato e dei dati. Di seguito sono elencati i punti principali dove viene impiegato; all’interno di tali sezioni sono fornite spiegazioni dettagliate su come il pattern interagisce con il sistema circostante:

\subsubsection{Observer}
\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{diagrammi_classi/pattern_utilizzati/PatternObserver.pdf}
    \caption{Rappresentazione del pattern Observer applicato nel modulo dei contatti fidati}
    \label{fig:pattern_observer}
\end{figure}
\paragraph{Descrizione del pattern:}\mbox{}\\
Il pattern Observer definisce la capacità per un oggetto \textit{Publisher} di definire un meccanismo di "iscrizione" per cui un insieme di oggetti \textit{Subscriber} può "osservarlo" ed essere notificato solo in seguito ad un suo cambiamento di stato. 

Nel contesto di Flutter, l'integrazione di questo pattern avviene tramite il binomio composto dal mixin \code{ChangeNotifier} e dal widget specializzato \code{Consumer}. Il \textit{ViewModel} agisce da \textit{Publisher}: ogni qualvolta rileva un cambiamento rilevante nei dati o nello stato, invoca il metodo \code{notifyListeners()} per segnalare la necessità di un aggiornamento. Il \textit{Consumer} funge da \textit{Subscriber}: esso è un widget che osserva e utilizza i dati forniti dal ViewModel e, ricevuta la notifica di cambiamento, innesca la ricostruzione automatica della propria interfaccia in modo reattivo. Questo meccanismo è fondamentale nel nostro caso poiché assicura che solo la porzione di interfaccia racchiusa nel \code{Consumer} (ovvero quella che effettivamente dipende dai dati mutati) venga aggiornata, ottimizzando le prestazioni ed evitando ricostruzioni costose e inutili dell'intera schermata.
\paragraph{Ragioni per l'utilizzo:}\mbox{}\\
L'uso principale del pattern nell'applicazione è nelle classi ViewModel, dato che permette di notificare solo i widget che richiedono modifiche dopo un cambiamento di stato del ViewModel, invece di dover ricostruire la schermata dopo una qualsiasi interazione, permettendo così una maggiore fluidità dell'interfaccia durante l'uso da parte dell'\term{Utente}. Inoltre il meccanismo di "iscrizione" rimuove la necessità di verifiche frequenti sullo stato del \textit{Publisher} da parte dei \textit{Subscriber} e rende il codice più facilmente estendibile e mantenibile dato che la modifica di una componente non va a influire sulle altre, per esempio, l'aggiunta di un widget alla \textit{View} non richiederebbe modifiche al \textit{ViewModel}.
\paragraph{Riferimenti nel progetto:}\mbox{}\\
Essendo strettamente interconnesso al MVVM, l'Observer pervade l'intera UI. Di seguito i punti principali dove i ViewModel agiscono da \textit{Publisher} per le rispettive schermate:
\begin{itemize}
    \item Autenticazione $\rightarrow$ \hyperref[DC-AuthViewModel]{\code{AuthViewModel}}
    \item Chatbot $\rightarrow$ \hyperref[DC-ChatbotViewModel]{\code{ChatbotViewModel}}
    \item Diario $\rightarrow$ \hyperref[DC-DiaryViewModel]{\code{DiaryViewModel}}
    \item Contatti Fidati $\rightarrow$ \hyperref[DC-TrustedContactViewModel]{\code{TrustedContactViewModel}}
\end{itemize}

\begin{figure}[H]

\subsubsection{Dependency Injection} \label{sec:pattern_dependency_injection}
\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{diagrammi_classi/pattern_utilizzati/PatternDependencyInjection.pdf}

    \label{fig:pattern_di}

\paragraph{Descrizione del pattern:}\mbox{}\\
Il pattern Dependency Injection (DI) è una tecnica in cui un oggetto riceve dall'esterno le istanze degli oggetti da cui dipende, anziché doverle creare internamente. Nel progetto viene adottata la forma di \textit{constructor injection}: le dipendenze vengono passate ai componenti direttamente come parametri del costruttore durante la fase di istanziazione.

Questo approccio permette di slegare i componenti logici dalla creazione delle proprie risorse. I \textit{ViewModel}, ad esempio, non istanziano mai i propri \textit{\term{Repository}}, ma li ricevono già configurati dal punto di ingresso del modulo o dell'applicazione, garantendo che ogni componente operi esclusivamente con le interfacce necessarie.
\paragraph{Ragioni per l'utilizzo:}\mbox{}\\
L'utilizzo della DI favorisce un'\term{Architettura} modulare e flessibile, riducendo l'accoppiamento tra le classi. Il vantaggio principale risiede nella testabilità: l'iniezione tramite costruttore permette di sostituire facilmente le dipendenze reali con oggetti fittizi (\textit{mock}), consentendo l'esecuzione di unit test in isolamento. Inoltre, centralizzare la logica di creazione degli oggetti facilita la manutenzione e l'eventuale sostituzione di implementazioni specifiche senza dover modificare i client che le utilizzano.
\paragraph{Riferimenti nel progetto:}\mbox{}\\
Il pattern è applicato diffusamente lungo l'intera struttura architetturale. Di seguito alcune classi che integrano attivamente questo approccio:
\begin{itemize}

\paragraph{Descrizione del pattern:}\mbox{}\\
Il pattern Command è un design pattern comportamentale che incapsula una richiesta come un oggetto autonomo, consentendo di parametrizzare i client con diverse richieste, accodare o registrare le esecuzioni e supportare operazioni annullabili. Nel contesto di un'applicazione Flutter governata dall'\term{Architettura} MVVM, il pattern Command è utilizzato per incapsulare e standardizzare le azioni invocabili dall'interfaccia \term{Utente} (ad esempio, recuperi di dati di rete, click di invio form o interazioni con il \term{Backend}), esponendo comandi robusti e isolati dal layer di View.
\paragraph{Ragioni per l'utilizzo:}\mbox{}\\
Questa soluzione architetturale favorisce un severo disaccoppiamento tra la componente visiva che invoca l'azione (la View) e il modulo deputato all'esecuzione logica (il ViewModel o strati inferiori). \subsubsection{Adapter} \label{sec:pattern_adapter}
\paragraph{Descrizione del pattern:}\mbox{}\\
Il pattern Adapter è un design pattern strutturale che permette l'interazione tra interfacce incompatibili, agendo come un mediatore che converte l'interfaccia di una classe in un'altra attesa dal client. Nell'applicazione, questo pattern viene impiegato per interfacciare il nucleo logico del sistema con servizi esterni, \term{Driver} o librerie di terze parti.
\paragraph{Ragioni per l'utilizzo:}\mbox{}\\
L'integrazione di questo pattern è fondamentale per preservare l'integrità della \textit{\term{Business Logic}}. Attraverso l'uso degli Adapter, i moduli centrali possono interagire con database o API esterne senza dipendere dai loro protocolli specifici o dai formati di dati grezzi. Questo isolamento garantisce che il cuore del sistema rimanga agnostico rispetto alle scelte tecnologiche infrastrutturali, facilitando sostituzioni o aggiornamenti di componenti esterni con un impatto minimo o nullo sul resto del codice.
\paragraph{Riferimenti nel progetto:}\mbox{}\\
Il pattern è impiegato nel layer di accesso ai dati. Viene utilizzato per mappare le risposte provenienti dai servizi esterni in oggetti di dominio validi per l'applicazione e, specularmente, per tradurre le richieste del sistema nel formato richiesto dai destinatari esterni, garantendo una comunicazione fluida tra layer con responsabilità differenti.


\subsection{Architettura di deployment} \label{subsec:architettura_deployment}

L'\term{Architettura} di \term{Deployment} del sistema si divide in due componenti principali: l'applicazione Client (eseguita sul dispositivo dell'\term{Utente}) e l'infrastruttura di \term{Backend} (eseguita in \term{Cloud}). Il sistema si basa su un paradigma \textbf{\term{Serverless}} ed \textbf{\term{Event-Driven}}, per garantire scalabilità, elevata disponibilità e abbattimento dei costi legati alla gestione manuale dei server.

\subsubsection{Client Mobile}
L'applicazione viene rilasciata come eseguibile nativo sui dispositivi mobili degli utenti (Android/iOS). Essendo sviluppata tramite il \term{Framework} \textbf{Flutter}, il codice scritto in Dart viene compilato in formato binario specifico per l'\term{Architettura} hardware del dispositivo ospite.
Il Client si interfaccia in modo del tutto indipendente ai servizi di \term{Backend} unicamente tramite la rete Internet, sfruttando protocolli di comunicazione sicuri.

\subsubsection{Infrastruttura AWS (Serverless Cloud)}
L'intero ecosistema di \term{Backend} è ospitato e gestito all'interno di \textbf{Amazon Web Services (AWS)}.
Questa scelta architetturale consente:
\begin{itemize}
    \item \textbf{\term{Scalabilità dinamica}}: le risorse allocate (il calcolo e lo storage) scalano o si accendono/spengono automaticamente in base al volume di richieste ricevute dai Client;
    \item \textbf{Isolamento e Sicurezza}: ogni funzione ha una specifica responsabilità e policy di accesso minima verso le altre risorse, limitando l'esposizione al minimo indispensabile;
    \item \textbf{Gestione del servizio (\term{Zero Ops})}: l'uso di infrastrutture completamente gestite e la persistenza dei dati automatizzata tramite \textbf{Amazon DynamoDB} e \textbf{Amazon S3} libera il team dagli oneri di manutenzione sistemistica.
\end{itemize}

Il flusso operativo del sistema e la connessione tra i componenti AWS si articolano nei seguenti layer di \term{Deployment}:
\begin{itemize}
    \item \textbf{Amazon API Gateway}: costituisce l'unico punto di ingresso espositivo e si occupa di orchestrare e bilanciare le richieste HTTP provenienti dal Client.
    \item \textbf{Amazon Cognito}: agisce come filtro primario in stretta collaborazione con l'API Gateway, validando i token \term{Utente} e negando le richieste non autorizzate.
    \item \textbf{AWS Lambda}: rappresenta il cuore elaborativo decentralizzato; l'infrastruttura crea dinamicamente container di esecuzione che accolgono le richieste smistate e processano la \term{Business Logic} interna.
    \item \textbf{Amazon DynamoDB e Amazon S3}: compongono lo strato di persistenza profondo ospitando, in alta disponibilità, i dati relazionali/JSON e i contenuti multimediali grezzi sollevando il livello server della necessità di memoria sul disco.
\end{itemize}

\subsubsection{Orchestrazione Event-Driven}
Oltre alle comunicazioni sincrone HTTP per le API \textit{REST}, l'\term{Architettura} di \term{Deployment} prevede un'orchestrazione asincrona fondamentale per le funzionalità dell'applicazione (es. le notifiche del sistema \textit{Dead Man's Switch}).
I componenti comunicano internamente tramite eventi gestiti da \textbf{Amazon EventBridge}, che funge da \textit{\term{Message Bus}} e permette:
\begin{itemize}
    \item \textbf{Comunicazione asincrona e disaccoppiata}: riducendo la dipendenza operativa tra i servizi;
    \item L'esecuzione ritardata e pianificata di check sui dati salvati nel database;
    \item L'instradamento di Eventi critici e allerte verso il servizio \textbf{Amazon SES} per l'invio automatizzato di e-mail.
\end{itemize}

\subsubsection{Infrastructure as Code (IaC)}
Il \term{Deployment} materiale di tutte le risorse in ambiente AWS non è eseguito manualmente, ma viene automatizzato in modo riproducibile attraverso l'impiego di \textbf{AWS SAM (\term{Serverless} Application Model)} e \textbf{AWS CloudFormation}. L'infrastruttura logica e fisica è versionata sotto forma di file \term{YAML}, aderendo interamente al paradigma dell'\textit{\term{Infrastructure as Code}}.

\subsubsection{Dead Man's Switch} \label{subsubsec:architettura_dead_man_switch}

La funzionalità del \textit{Dead Man's Switch} (Interruttore dell'Uomo Morto) rappresenta un sistema di sicurezza critico che invia avvisi automatici in caso di inattività prolungata dell'\term{Utente}. L'\term{Architettura} frontend è focalizzata sulla gestione sicura della configurazione di tale sistema. Il frontend non interagisce direttamente con servizi di posta elettronica, ma demanda la gestione dei timer e l'invio delle email tramite AWS SES al \term{Backend}, garantendo così la sicurezza e l'affidabilità del servizio anche ad applicazione chiusa. Analogamente al resto dell'applicazione, la funzionalità è implementata secondo il pattern MVVM e le linee guida architetturali di Flutter, distinguendo un \term{Data Layer}, composto da Service e \term{Repository}, e un \term{UI Layer}, composto da View e ViewModel.

\paragraph{\term{Architettura} e Flusso di Autenticazione: Modulo Federated Login}\mbox{}\\
La presente sezione descrive l'\term{Architettura} logica e il flusso dei dati relativi al modulo di autenticazione e autorizzazione dell'applicazione. Il sistema adotta un modello di federated login basato su Amazon Cognito integrato con Google come Identity Provider (IdP), progettato per garantire un accesso sicuro e standardizzato alle risorse di \term{Backend} senza demandare la gestione crittografica delle credenziali all'applicazione client.

\paragraph{Iniziazione del Flusso e Autenticazione Federata}\mbox{}\\
Il \term{Processo} di autenticazione ha inizio quando l'\term{Utente} interagisce con l'applicazione client (Flutter) richiedendo l'accesso al sistema. L'applicazione delega interamente la gestione dell'identità inoltrando una richiesta di login ad Amazon Cognito. Cognito, fungendo da Service Provider, intercetta la richiesta e avvia una procedura di autenticazione basata sullo standard OpenID Connect (OIDC) delegandola ai server di Google. L'\term{Utente} completa la fase di riconoscimento interfacciandosi direttamente con l'infrastruttura del provider esterno. A seguito della corretta \term{Verifica} delle credenziali, Google restituisce ad Amazon Cognito un codice di autorizzazione attestante il successo dell'operazione e l'identità dell'\term{Utente}.

\paragraph{Emissione dei Token di Sessione}\mbox{}\\
Acquisita la conferma dal provider federato, Amazon Cognito processa il codice di autorizzazione e genera un set di token crittografici aderenti allo standard JWT (JSON Web Token). Questi token vengono trasmessi in modo sicuro all'applicazione mobile, concludendo la fase di autenticazione. Da questo momento, il client dispone di una prova di identità verificata e utilizzerà l'Access Token JWT per autorizzare le successive chiamate di rete dirette ai servizi di \term{Backend}.

\paragraph{\term{Validazione} Perimetrale e Instradamento Sicuro}\mbox{}\\
Per accedere alle logiche applicative, l'app Flutter compone una richiesta HTTPS indirizzata all'Amazon API Gateway, includendo il token JWT nelle intestazioni di autorizzazione. L'API Gateway assume il ruolo di strato di sicurezza perimetrale (edge security). Prima di instradare il traffico, il Gateway utilizza un Cognito Authorizer nativo per eseguire un rigoroso controllo di validità sul token ricevuto. Tale procedura \term{Verifica} l'autenticità della firma crittografica, l'integrità del \term{Payload} e la validità temporale della sessione direttamente contro le configurazioni dello User Pool di Cognito.

Questa specifica impostazione architetturale assicura che qualsiasi richiesta malevola, non autorizzata o provvista di credenziali scadute venga respinta al livello di rete. Solamente le richieste che superano con successo la \term{Validazione} del token vengono instradate dall'API Gateway verso la specifica funzione AWS Lambda designata, garantendo che le risorse computazionali elaborino esclusivamente traffico certificato e sicuro.

\paragraph{\term{Architettura} e Flusso di Elaborazione: Modulo Luoghi Sicuri}\mbox{}\\
Il modulo "Luoghi Sicuri" è stato ingegnerizzato adottando una rigorosa separazione delle responsabilità (\textit{\term{Separation of Concerns}}) tra l'elaborazione lato client (Frontend) e l'infrastruttura \term{Cloud} (\term{Backend}). L'obiettivo primario è stato quello di minimizzare il carico computazionale server-side ed eliminare del tutto i costi legati ai calcoli geospaziali.

Il flusso di elaborazione si articola nei seguenti passaggi:
\begin{itemize}
    \item \textbf{Ingestione della Richiesta}: L'\term{Utente} accede alla sezione della mappa tramite l'applicazione. Il client Flutter genera una richiesta HTTPS (metodo \texttt{GET /safe\_locations}).
    \item \textbf{Instradamento verso Lambda}: API Gateway intercetta la richiesta, ne valida il contesto e la inoltra alla funzione AWS Lambda dedicata alla gestione dei luoghi sicuri.
    \item \textbf{Accesso ai dati e logica applicativa}: la Lambda esegue la logica applicativa necessaria e recupera i dati dal bucket S3 dedicato. Al suo interno sono infatti memorizzati sia i metadati descrittivi, sia le coordinate geospaziali (latitudine e longitudine) per ciascun punto di interesse.
    \item \textbf{Elaborazione e serializzazione}: la funzione Lambda elabora i dati estratti e li converte in un \term{Payload} JSON standardizzato e ottimizzato per il consumo lato client.
    \item \textbf{Risposta al client}: API Gateway inoltra la risposta HTTP \texttt{200 OK} al client Flutter contenente l'elenco dei luoghi sicuri.
\end{itemize}

\paragraph{Delega della Logica Geospaziale al Livello Client (Edge Computing)}\mbox{}\\
Al fine di ottimizzare ulteriormente i costi, l'intera logica di rendering visivo e di routing è delegata all'applicazione sul dispositivo dell'\term{Utente}. Il \term{Backend} AWS si configura esclusivamente come Data Provider di coordinate statiche. Alla ricezione del \term{Payload} JSON, l'applicativo Flutter si fa carico di istanziare la mappa nativa e posizionare i marker grafici (pin). L'azione di navigazione guidata (es. pulsante "Portami lì") sfrutta le Intents (su Android) o le URL Schemes (su iOS) del sistema operativo per invocare applicazioni di navigazione di terze parti (come Google Maps o Apple Maps). Questo approccio demanda il tracciamento GPS e il calcolo dinamico dell'itinerario al dispositivo locale, garantendo la scalabilità infinita del sistema AWS anche in condizioni di massiccio utilizzo concorrente.

\paragraph{API associate}\mbox{}\\
\begin{itemize}
    \item \texttt{GET /safe\_locations/}: ritorna le informazioni di tutti i luoghi sicuri.
\end{itemize}
\textit{Nota di sicurezza}: L'integrazione di un Authorizer Cognito per la \term{Verifica} delle autorizzazioni è stata deliberatamente omessa per questa rotta. L'assenza dell'Authorizer in quest'area è difatti una scelta architetturale mirata a rimuovere complessità infrastrutturale non necessaria e ad abbattere i costi operativi associati al recupero di questi specifici dati.

\subsubsection{Diario criptato e fittizio} \label{subsubsec:architettura_diari}

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{diagrammi_architettura/diari/diari.pdf}
    \caption{\term{Architettura} diari}
    \label{fig:architettura_diari}
\end{figure}

\paragraph{\term{Architettura} e Flusso di Elaborazione: diario criptato e fittizio}\mbox{}\\
La sezione dedicata al diario criptato e fittizio è progettata per garantire la sicurezza delle informazioni dell'\term{Utente} e la corretta gestione e archiviazione di diverse tipologie di dati, quali contenuti testuali, immagini e tracce audio. A differenza delle altre funzionalità, il diario è l'unico componente protetta da una password aggiuntiva, distinta da quella utilizzata per l'account principale.

Questo approccio consente all'applicazione di fornire accesso a risorse differenti in base alla password inserita, dato che i due diari sono protetti da credenziali separate. Poiché Amazon Cognito non supporta direttamente flussi di autenticazione di questo tipo, la gestione dell'accesso al diario avviene tramite la memorizzazione in DynamoDB degli hash delle due password. Quando l'\term{Utente} tenta l'accesso, viene generato l'hash della password inserita tramite Argon2id. Questo hash viene quindi confrontato con quello salvato nella tabella utenti. In caso di corrispondenza, la password fornita viene utilizzata per derivare una chiave crittografica, impiegata per decifrare le note del diario corrispondente. In entrambi i casi viene utilizzato Argon2id, ma con parametri di memory cost, time cost, salt length e parallelism diversi.

Una volta completato con successo l'accesso, viene creata una sessione lato \term{Backend}, così da rendere più efficienti le successive operazioni CRUD. La creazione della sessione consiste nella generazione di un token casuale che viene inviato in risposta al client. Tale token ha durata limitata e viene memorizzato nella tabella DynamoDB relativa all'accesso al diario. In caso di un numero di tentativi di accesso errati superiore alla soglia consentita, viene applicato un meccanismo di timeout incrementale che blocca temporaneamente ulteriori tentativi.

L'archiviazione delle note avviene su due servizi AWS distinti. I contenuti testuali sono memorizzati in DynamoDB, che mantiene le informazioni per ciascun \term{Utente} e per ciascun diario. I file binari, come immagini e tracce audio, sono invece salvati in bucket S3. Il recupero di tali risorse avviene tramite URL \textit{presigned}, al fine di ridurre la quantità di dati trasferiti sulla rete.

Il flusso di elaborazione è dunque il seguente:
\begin{itemize}
    \item \textbf{Invio della Richiesta di Autenticazione}: L'\term{Utente} inserisce la password del diario tramite app. Il client genera una richiesta HTTPS (metodo \texttt{POST /diary/auth/}) includendo la password nel body della richiesta.
    
    \item \textbf{\term{Verifica} delle Credenziali}: API Gateway \term{Verifica} che l'\term{Utente} sia autenticato all'applicazione. Dopodiché inoltra la richiesta alla funzione Lambda, che calcola l'hash della password ricevuta e lo confronta con gli hash memorizzati in DynamoDB. In caso di corrispondenza, viene identificato il tipo di diario associato.
    
    \item \textbf{Derivazione della Chiave Crittografica}: La funzione Lambda utilizza la password fornita per derivare una chiave crittografica tramite Argon2id, impiegando un salt dedicato. Tale chiave viene utilizzata per le successive operazioni di decrittazione.
    
    \item \textbf{Creazione della Sessione}: A seguito dell'autenticazione, il \term{Backend} genera una sessione associata all'\term{Utente}, che consente di effettuare operazioni sul diario senza ripetere il \term{Processo} di autenticazione per ogni richiesta.
    
    \item \textbf{Recupero delle Note}: Quando l'\term{Utente} richiede di recuperare la lista di note di uno dei diari (metodo \texttt{GET /diary/\{diary\_type\}/}), API Gateway invia la richiesta alla Lambda, che recupera le \textit{preview} dal database DynamoDB e le restituisce al client.
    
    \item \textbf{Recupero di una Nota}: Per ottenere il contenuto completo di una nota (metodo \texttt{GET /diary/\{diary\_type\}/\{note\_id\}/}), la Lambda recupera i dati cifrati da DynamoDB e gli eventuali riferimenti a file su S3, decrittando il contenuto tramite la chiave derivata e restituendolo al client.
    
    \item \textbf{Gestione dei Contenuti Binari}: In presenza di immagini o tracce audio, la Lambda genera URL presigned per gli oggetti memorizzati su S3, permettendo al client di accedere direttamente alle risorse senza transitare attraverso il \term{Backend}.
    
    \item \textbf{Operazioni di Scrittura}: Per la creazione o modifica di note (metodi \texttt{POST /diary/\{diary\_type\}/} e \texttt{PUT /diary/\{diary\_type\}/\{note\_id\}/}), la Lambda cifra i contenuti tramite la chiave derivata e li memorizza in DynamoDB, salvando eventuali file binari su S3.
    
    \item \textbf{Eliminazione delle Note}: In caso di richiesta di eliminazione (metodo \texttt{DELETE /diary/\{diary\_type\}/\{note\_id\}/}), la Lambda rimuove i dati associati dal database e, se presenti, elimina anche i file binari corrispondenti dai bucket S3.
\end{itemize}

\paragraph{API associate}\mbox{}\\
\begin{itemize}
    \item \texttt{POST /diary/auth/}: invia la password per l'autenticazione; ritorna l'esito dell’autenticazione e il tipo di diario associato.
    
    \item \texttt{GET /diary/\{diary\_type\}/}: ritorna le \textit{preview} di tutte le note del diario specificato.
    \item \texttt{POST /diary/\{diary\_type\}/}: crea una nuova nota per l’\term{Utente} nel diario specificato.
    
    \item \texttt{GET /diary/\{diary\_type\}/\{note\_id\}/}: ritorna il contenuto completo della nota specificata.
    \item \texttt{PUT /diary/\{diary\_type\}/\{note\_id\}/}: aggiorna la nota specificata nel database.
    \item \texttt{DELETE /diary/\{diary\_type\}/\{note\_id\}/}: rimuove la nota specificata.
\end{itemize}

\begin{figure}[H]

\paragraph{\term{Architettura} e Flusso di Elaborazione: chatbot (detective delle relazioni e specchio intelligente)}\mbox{}\\
L'\term{Architettura} di \term{Backend} dedicata al chatbot è progettata per gestire conversazioni persistenti tra \term{Utente} e modello linguistico, garantendo scalabilità, efficienza nell’accesso ai dati e qualità delle risposte generate.

API Gateway rappresenta il punto di ingresso per tutte le richieste client e si occupa della \term{Verifica} dell’autenticazione dell’\term{Utente}. Una volta validata la richiesta, questa viene inoltrata a una funzione Lambda che implementa la logica applicativa del chatbot, inclusa la gestione delle chat e l’interazione con il modello linguistico.

Le conversazioni sono strutturate come entità persistenti (chat), ciascuna identificata da un \texttt{chat\_id} univoco all'interno dell'intero sistema. Ogni chat contiene una sequenza di messaggi (\term{Utente} e assistente artificiale), memorizzati in DynamoDB. Per ottimizzare le prestazioni e ridurre il carico di rete, le operazioni di recupero dello storico restituiscono esclusivamente le informazioni di sintesi (ad esempio titolo e metadata), mentre il contenuto completo viene fornito solo su richiesta esplicita.

Quando l’\term{Utente} invia un messaggio, il sistema non si limita a inoltrarlo direttamente al modello, ma recupera le informazioni più rilevanti dalla chat in corso. In particolare, la Lambda recupera il contesto rilevante della conversazione dalla base di dati (DynamoDB), costruendo un prompt arricchito che include la cronologia significativa dei messaggi. Per estrarre tali informazioni, la Lambda utilizza tecniche di ricerca lessicale basate su BM25, evitando di concatenare l'intera conversazione al testo inviato dall'\term{Utente}. Questo approccio consente di migliorare la coerenza e la pertinenza delle risposte generate dal modello.

Il prompt così costruito viene inviato a Bedrock, che restituisce la risposta generata dal LLM. La risposta, insieme al messaggio dell’\term{Utente}, viene quindi memorizzata in DynamoDB come parte della chat. Nel caso in cui il messaggio inviato sia il primo di una nuova chat, la Lambda imposta il titolo della chat alle prime tre parole del messaggio dell'\term{Utente}.

Il flusso di elaborazione è dunque il seguente:
\begin{itemize}
    \item \textbf{Invio della Richiesta}: L’\term{Utente} interagisce con il chatbot tramite app, generando una richiesta HTTPS verso uno degli endpoint disponibili (ad esempio \texttt{POST /chats/\{chat\_id\}/messages}).
    
    \item \textbf{Autenticazione}: API Gateway \term{Verifica} che l’\term{Utente} sia autenticato all’applicazione. In caso positivo, la richiesta viene inoltrata alla funzione Lambda responsabile della logica del chatbot.
    
    \item \textbf{Gestione della Chat}: La Lambda identifica la chat di riferimento tramite \texttt{chat\_id}. Se necessario, recupera i metadati o \term{Verifica} l’esistenza della chat in DynamoDB.
    
    \item \textbf{Recupero del Contesto (RAG)}: Prima di inviare il messaggio al modello, la Lambda esegue una query su DynamoDB per ottenere i messaggi precedenti rilevanti della conversazione, costruendo il contesto da includere nel prompt.
    
    \item \textbf{Costruzione del Prompt}: Il messaggio dell’\term{Utente} viene combinato con il contesto recuperato, formando un prompt strutturato da inviare al modello linguistico.
    
    \item \textbf{Invocazione del Modello}: La Lambda invia il prompt a Bedrock, che elabora la richiesta e restituisce una risposta generata.
    
    \item \textbf{Persistenza dei Messaggi}: La Lambda salva sia il messaggio dell’\term{Utente} sia la risposta del modello in DynamoDB, associandoli alla chat corrente.
    
    \item \textbf{Aggiornamento dei Metadati}: Se necessario, la Lambda aggiorna le informazioni della chat (ad esempio titolo o timestamp dell’ultima attività).
    
    \item \textbf{Restituzione della Risposta}: La risposta generata dal modello, insieme ai metadati aggiornati, viene restituita al client.
    
    \item \textbf{Recupero dello Storico}: Quando l’\term{Utente} richiede la lista delle chat (metodo \texttt{GET /chats/}), la Lambda restituisce solo le \textit{preview} delle chat, senza includere l’intero contenuto dei messaggi.
    
    \item \textbf{Recupero di una Chat}: Per ottenere il contenuto completo di una chat (metodo \texttt{GET /chats/\{chat\_id\}}), la Lambda recupera tutti i messaggi associati da DynamoDB e li restituisce al client.
    
    \item \textbf{Operazioni CRUD}: Le operazioni di creazione, aggiornamento ed eliminazione delle chat vengono gestite direttamente dalla Lambda tramite interazioni con DynamoDB.
\end{itemize}

\paragraph{API associate}\mbox{}\\
\begin{itemize}
    \item \texttt{GET /chats/}: ritorna le \textit{preview} di tutte le chat dell’\term{Utente}.
    \item \texttt{POST /chats/}: crea una nuova chat per l’\term{Utente}.
    
    \item \texttt{GET /chats/\{chat\_id\}}: ritorna la chat specificata con il contenuto completo dei messaggi.
    \item \texttt{PUT /chats/\{chat\_id\}}: aggiorna i dati della chat specificata.
    \item \texttt{DELETE /chats/\{chat\_id\}}: rimuove la chat specificata dal database.
    
    \item \texttt{POST /chats/\{chat\_id\}/messages}: invia un messaggio al modello linguistico; ritorna la risposta generata e il titolo aggiornato della chat.
\end{itemize}

\paragraph{\term{Architettura} e Flusso di Elaborazione: contatti fidati, SOS e Dead man's switch}\mbox{}\\
La sezione relativa ai contatti fidati, all’invio di messaggi di emergenza e al meccanismo di Dead man's switch è progettata per garantire la gestione automatizzata dello stato di attività dell’\term{Utente} e la possibilità di attivare procedure di emergenza sia manualmente che in modo automatico.

API Gateway gestisce l’esposizione delle API e \term{Verifica}, per ogni richiesta, che l’\term{Utente} sia correttamente autenticato all’applicazione. Le richieste valide vengono inoltrate a una funzione Lambda centrale, responsabile della gestione della logica applicativa relativa ai contatti fidati, alla configurazione del Dead man's switch e all’orchestrazione dell’invio delle email tramite Amazon SES.

I dati sono memorizzati su due database DynamoDB distinti:
\begin{itemize}
    \item \texttt{dms\_config\_mvp}: contiene la configurazione del Dead man's switch, includendo il titolo e il corpo dell’email di inattività, il primo e secondo timer di inattività, l’ultimo accesso dell’\term{Utente} e lo stato corrente del sistema (attivo, prima inattività, seconda inattività).
    
    \item \texttt{trusted\_contact\_mvp}: memorizza le informazioni relative ai contatti fidati associati a ciascun \term{Utente}, inclusi nome, email e numero di telefono.
\end{itemize}

Il sistema implementa inoltre un meccanismo di monitoraggio automatico basato su AWS EventBridge. Uno scheduler giornaliero attiva la Lambda centrale che \term{Verifica} lo stato di attività degli utenti e determina eventuali condizioni di inattività prolungata.

Il flusso di elaborazione del Dead man's switch è il seguente:
\begin{itemize}
    \item \textbf{Trigger programmato}: EventBridge attiva quotidianamente la Lambda, che avvia il controllo dello stato degli utenti.
    
    \item \textbf{Recupero configurazioni}: la Lambda effettua il fetch dei dati presenti in \texttt{dms\_config\_mvp}, ottenendo i timer di inattività, l’ultimo accesso registrato e lo stato corrente del Dead man's switch.
    
    \item \textbf{Valutazione dello stato di inattività}: la funzione confronta il tempo corrente con l’ultimo accesso dell’\term{Utente}. Se viene superata la prima soglia di inattività, il sistema entra nello stato di “prima inattività”. Al raggiungimento della seconda soglia di inattività, viene attivato lo stato di “seconda inattività”.
    
    \item \textbf{Invio email di prima inattività}: al superamento della prima soglia, la Lambda invia tramite Amazon SES un’email all’\term{Utente} utilizzando il titolo e il corpo configurati, notificando lo stato di inattività.
    
    \item \textbf{Attivazione SOS (seconda inattività)}: al superamento della seconda soglia, la Lambda recupera l’elenco dei contatti fidati da \texttt{trusted\_contact\_mvp} e invia, tramite SES, un’email di SOS predefinita a ciascun contatto.
    
    \item \textbf{Aggiornamento stato}: lo stato del sistema viene aggiornato in DynamoDB per evitare invii ripetuti non necessari.
\end{itemize}

Oltre al flusso automatico, il sistema supporta l’invio manuale di SOS e la gestione in tempo reale dello stato di attività dell’\term{Utente} tramite heartbeat.

Il flusso di heartbeat è il seguente:
\begin{itemize}
    \item \textbf{Invio heartbeat}: All'avvio dell'app, il client invia una richiesta all'API \texttt{POST /dms/heartbeat/} per notificare l’utilizzo attivo dell’applicazione.
    
    \item \textbf{Aggiornamento stato \term{Backend}}: la Lambda aggiorna il campo “ultimo accesso” nella tabella \texttt{dms\_config\_mvp} e, se necessario, resetta lo stato di inattività.
\end{itemize}

L’invio SOS \textbf{manuale} segue invece il seguente flusso:
\begin{itemize}
    \item \textbf{Richiesta di emergenza}: il client invia una richiesta HTTPS all'API \texttt{POST /trusted\_contacts/sos/}.
    
    \item \textbf{Recupero contatti}: la Lambda recupera tutti i contatti fidati associati all’\term{Utente} da \texttt{trusted\_contact\_mvp}.
    
    \item \textbf{Invio email SES}: la funzione Lambda invia immediatamente un'email di emergenza a tutti i contatti fidati tramite Amazon SES.
\end{itemize}

La gestione dei contatti fidati è completamente CRUD e permette all’\term{Utente} di mantenere aggiornato il proprio elenco di destinatari di emergenza.

\paragraph{API associate}\mbox{}\\
\begin{itemize}
    \item \texttt{GET /dms/}: restituisce tutte le opzioni configurabili del Dead man's switch, incluse soglie di inattività e template email.
    \item \texttt{POST /dms/}: salva o aggiorna la configurazione del Dead man's switch dell’\term{Utente}.
    
    \item \texttt{POST /dms/heartbeat/}: registra il segnale di attività dell’\term{Utente} aggiornando l’ultimo accesso.
    
    \item \texttt{GET /trusted\_contacts/}: restituisce la lista dei contatti fidati associati all’\term{Utente}.
    \item \texttt{POST /trusted\_contacts/}: crea un nuovo contatto fidato.
    \item \texttt{PUT /trusted\_contacts/\{trusted\_contact\_id\}/}: aggiorna un contatto fidato esistente.
    \item \texttt{DELETE /trusted\_contacts/\{trusted\_contact\_id\}/}: elimina un contatto fidato.
    
    \item \texttt{POST /trusted\_contacts/sos/}: attiva manualmente l’invio di una email di emergenza a tutti i contatti fidati.
\end{itemize}
